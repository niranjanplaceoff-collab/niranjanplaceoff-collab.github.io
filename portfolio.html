Aircraft TCP Telemetry Simulation Framework

October 2026 · C · Linux · POSIX threads · TCP/IP

An eight-channel telemetry simulator that behaves like an aircraft sending data to a ground station. Each channel runs on its own thread and sends frames over a TCP client–server link, so the receiver has to cope with several data streams at once, as an avionics system does.

What I built

  • Eight concurrent telemetry channels using POSIX multithreading in C on Linux.
  • A TCP/IP client–server link with acknowledgement and frame tracking, so every frame sent can be matched to a frame received.
  • A fault injection mechanism that creates communication problems on purpose, to see how the system reacts.
  • Structured logging of every frame, so a run can be reviewed afterwards.

How I tested it

  • Measured latency, jitter, throughput and frame delivery for each run.
  • Compared normal runs with fault-injected runs to see where frames were delayed or lost.

Flight Management System, Software-in-the-Loop

April 2026 · C · MATLAB/Simulink · TCP · Linux

A flight management architecture tested entirely in software. A MATLAB/Simulink model acts as the aircraft and talks over TCP to a navigation server I wrote in C on Linux. This is the software-in-the-loop approach used to check flight logic before it runs on real hardware.

What I built

  • A C server on Linux that performs the navigation calculations: distance and bearing between positions.
  • Waypoint sequencing, so the system moves through a flight plan one waypoint at a time.
  • A TCP client in MATLAB/Simulink that sends aircraft state and receives navigation results, forming a closed simulation loop.

How I worked

  • Followed DO-178C-inspired development practices for the software.
  • Considered DO-330-inspired principles for qualifying the tools used.

ESP32 IMU Sensor Health and Fault Monitoring

June 2026 · ESP32 · I²C · MPU6050 · Wokwi

A monitor that checks whether an inertial sensor can be trusted. Flight systems depend on accelerometer and gyroscope data, so this project reads a six-axis MPU6050 over I²C and decides in real time whether its readings are healthy.

What I built

  • Data acquisition from the MPU6050 accelerometer and gyroscope over I²C.
  • Range checks, which catch values outside what the sensor can physically report.
  • Plausibility checks, which catch values that are in range but don’t make sense.
  • Timeout checks, which catch a sensor that has stopped responding.
  • Fault classification and status indication, so the type of fault is clear at a glance.

How I tested it

  • Ran controlled fault-injection tests in the Wokwi simulator, and checked that each injected fault was detected and classified correctly.

ADAS Prototype on NVIDIA Jetson Nano

November 2025 · Python · Jetson Nano · ESP32 · RTOS concepts

A driver-assistance prototype that runs on an NVIDIA Jetson Nano and combines camera vision with distance sensors. It watches the road, watches the driver, and triggers a safety response when something looks wrong. It shows the same ideas avionics relies on: several inputs, timing, and a safe reaction.

What I built

  • Vision on the Jetson Nano, written in Python and run directly on the board: lane detection, vehicle detection and traffic-sign recognition.
  • Sensor fusion that combines the camera results with IR and ultrasonic distance readings from ESP32 units, so the safety decision uses more than one source.
  • Driver drowsiness monitoring, so the system reacts to the driver as well as the road.
  • A sensor-based safety response that acts on the fused data.
  • RTOS scheduling concepts applied to organise the camera, sensor and alert work as separate tasks with timing in mind.
